## ① 转录恢复态心智【实测】

实测动线（打包版）：转 phone.wav 完成 → 强杀重启 → 转录页直接显示「1 segments · phone.wav」+ 完整结果（实拍）；transcribe-last.json 实查只含 segments+fileName，完成才写。

- **恢复正确性**：重启懒加载恢复通过；来源文件名灰字紧跟段数，用户能对上「这是哪个文件的结果」。
- **恢复态下操作自然度**：导出 TXT 默认文件名 `phone`（原文件名前缀，实拍）；恢复态直接拖新文件正常开转、旧结果被新进度替换，动线顺畅；无 running 态则无 Cancel 按钮，无歧义。
- **恢复态 vs 刚完成态区分**：两者视觉完全一致，唯一线索是文件名。单文件场景够用；但没有时间戳，隔几天再开应用无法判断「这是什么时候转的」。→ 观察-1（不立案）：json 里加 `finishedAt`，恢复态文件名旁补一句灰字「上次转录 · {日期}」，~10 行。
- **转录中途退出**【实测】：转 long10min.wav 至 ~40% 强杀 → json 原样保留上一个完成结果（phone.wav）不被半截覆盖（正确，取消/失败不写实证：Cancel 后 json 仍为 phone.wav）→ 重启后页面显示的是 phone.wav 旧结果。部分进度静默作废且无提示。→ 观察-2（不立案）：中途退出属用户主动行为、重跑成本可控；若要做，退出时 running 态弹一次确认即可（~15 行），优先级低于多会话演进。

## ② 单结果持久化的产品边界评估

「只存最后一次」何时咬人（场景推演，【推测】标注；机制均已实测核对）：

1. **转完 A 又转 B，想找回 A**——A 的结果被 B 覆盖（机制实测：新完成即整写 json），若 A 没导出即永久丢失。会议室连转两个录音的用户第一次遇到就会困惑「刚才那个去哪了」。
2. **恢复态误拖错文件**——旧结果立即被替换，无撤销。
3. **想引用上周转录的一句话**——没有任何检索入口（历史页不含转录，实测核对）。

对比 MacWhisper：多会话 .whisper 文件 + 全文搜索【官方，第 81 轮核对】。

**最小演进建议**（如无异议按此列入候选）：不建议直接抄多会话文件管理（重 UI）；建议「转录进历史」——完成时把全文+文件名+时间作为一条 kind=transcribe 的历史条目入 history.json（历史页已有搜索/导出/500 条淘汰全套基建，复用即可，~40 行）；transcribe-last.json 保留作页面恢复态。覆盖上面三个场景，成本远低于会话列表。
