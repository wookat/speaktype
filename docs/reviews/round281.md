## 专项 1：自动纠错学习链路深度审查

1. RightCtrl 说该句落字 Notepad；
2. 观察窗内把「答复」手动改为「回执」；
3. 点击 SpeakType 窗口（blur 立即结算）。

证据：

### b) 学入后复用纠正 —【实测】通过

学入「答覆」后再说同一句，落字直接产出「…给他答覆」（截图 ss_11f259af；本轮核心回归 Alt+Q 段落亦复现「给他答覆。」，见 ss_f08562fb），无需再改。

### 281-P3-1 粘贴覆盖大段内容会被当作纠错学入词典（误学）

- 复现：RightCtrl 落字整句 → 观察窗内全选（或选中大段）→ Ctrl+V 粘贴不相关新内容 → blur 结算。
- 现象【实测】：diff 推断把整段替换当作两条"纠错"学入，日志：
  - `auto-learn: "帮我跟老板说，那个方案需要再改一下，明天" -> "今天"`
  - `auto-learn: "之前给他答覆" -> "开会讨论预算"`
  （18:43:46，两条同时产生；测试中已 Undo 移除，未残留 hotwords。）
- 影响面：用户落字后用粘贴方式重写内容是常见操作；学入的长短悬殊映射会污染热词表，后续识别可能被错误"纠正"，且用户若没注意 toast 不会察觉。
- 修复建议：对 diff 结果加护栏——原文/替换文长度比超阈值、替换跨越多个分词边界、或编辑事件为单次大段粘贴（剪贴板长度≈插入长度）时不学习；只学习"近长度、局部"的词级替换。
- 严重级：P3（有 toast+Undo 可挽回，且需粘贴覆盖这一特定路径触发）。

环境：`npx wrangler dev`（127.0.0.1:8787，首次因系统缺 VC++ 运行库崩溃 `0xc0000005`，装 vc_redist.x64 后正常——环境问题非产品问题）；桌面端 `settings.remoteRelayUrl=https://127.0.0.1:8443`（本地 TLS 代理→8787），日志确认 `remote mic relaying via https://127.0.0.1:8443/m/...`。两个独立 profile Chrome（fake mic）经 CDP 同时导航同一房间。

### 毫秒级同时加入 —【实测】通过

两页导航请求间隔 23–28ms：后连成功者胜出（「已连接电脑」按钮可用），另一方明确提示「该房间已有手机连接」且按钮禁用置灰。两次运行行为一致，无双推流。

### 快速交替按住说话 12 轮 —【实测】通过

脚本节奏：被禁用方 reload 抢占 → 立即按住 2s → 松开，A/B 交替 12 轮（间隔 ~4.5s）：

- 12 轮 → 桌面日志恰好 12 条 `dictation finalize`（19:03:xx–19:04:xx），history 新增 12 条 `source:"phone"` 条目，文本均为同一 WAV 片段的正确识别（"帮我跟老板"），**无串音、无丢字、无多落**；
- 每轮被顶替方状态即时变为「该房间已有手机连接」+ 按钮禁用并复位为「按住说话」（12/12 轮一致，无一卡在「松手结束」）；
- 桌面端无残留胶囊、无崩溃，SpeakType 进程与设置窗口正常（截图 ss_3d3bb134）。

### 280-P3-1 修复确认（录音中被抢占）—【实测】已修复

专项脚本：A 按住录音中（页面「录音中…/松手结束」）→ B 抢占加入 → B 立即按住说话：

- A 页面即刻复位：「该房间已有手机连接」+ 按钮恢复「按住说话」并禁用——不再卡「松手结束」（PR #370 生效）；
- B 抢占后**第一次按住即被接受**（产生 finalize，未被 busy 拒绝）——桌面端已同步取消 A 的进行中会话（PR #371 生效）。
- 附带发现（非立案）：另一次运行中因夹具（touch 事件未配对释放）造成"卡按住"会话时，B 抢占同样成功清理并恢复可用，进一步佐证 #371 的取消路径健壮。
- 保持既有设计：被抢占方进行中的语音被丢弃（不落字、不提示"这段话丢了"），280 轮已判定该取舍可接受，本轮不再立案。
