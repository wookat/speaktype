## 一、#84/#85 回归：正向链路通过，但发现一个多处修改的实质缺陷

### 1. 英文自动学词正向链路——【实测】通过（上轮空壳闭环）
Parakeet 口述落字 "The final report is ready for your review." → 记事本内把 "report" 整词改成 "Bericht" → 停顿后日志 `auto-learn: "report" -> "Bericht"`，词典出现 `Bericht`。词边界外扩生效（共后缀 t 不再把词拆碎）。#85 的入口门槛（英文句也启动观察）同步验证——观察进程对纯英文落字确实在跑。

### 2. P2-1（本轮最重要发现）：同一停顿窗口改两个词 → 学进碎词垃圾
- 【实测】口述落字 "Please send the report before the review tomorrow." → 同一轮编辑先改 "review"→"feedback" 再改 "report"→"summary"（1.5 秒内完成）→ 日志：
  ```
  auto-learn: "the " -> "summa"
  auto-learn: "w" -> "dback"
  ```
  词典被塞进 **`summa` 和 `dback` 两个碎词**。
- 【源码】根因：`extractCorrections` 的"两侧均为单个英文词"快捷路径只覆盖单处修改；多处修改落入 LCS 字符级对齐，英文单词被拆成碎片，而词边界外扩只做在外层去前后缀处、**没有做在 LCS 产出的每个 diff 上**；`MAX_SEGMENT` 从 10 放宽到 20 后碎片更容易漏过。
- 危害评估：主动污染有限（碎词命中真实口述的概率低），但 Manage hotwords 里会静默积累垃圾词、且 `"the " -> "summa"` 这类 diff 连 wrong 都不是词。中文侧不受影响（CJK 门槛天然挡住碎片）。
- 修复建议（~10 行）：LCS 每个 diff 也做词边界吸附（向两侧扩到完整 token）；或英文 learnable 增加整词校验——`inserted` 中 `wrong` 的出现位置前后必须是非字母数字。配反例入回归清单：一轮改两个词，各自学到完整词或都不学。

### 3. P3：纯大小写修正也会学词
【函数级】"report"→"Report" 会学进 `Report`，此后所有 "report" 落字被全局改写为大写。这可能正是用户想要的（专有名词），也可能是句首重排的误伤。属产品决策：若要排除，学词时要求 wrong/right 大小写不敏感地不同（1 行）；建议先观察真实反馈再定。

## 二、产品决策论证：中文单字剩余是否做词边界外扩——建议做保守版

任务给的场景（明天→后天，去共同后缀"天"剩单字 明→后 被拒学）分两类看：

1. **语义改写类（明天→后天）**：这不是识别错误，学不到是**正确行为**——但即使学了危害也有限：中文应用侧是拼音同音门槛（明天 mingtian ≠ 后天 houtian，学了也永远不会触发替换），代价只是词典噪声。
2. **真识别错误类（名天→明天、语音→雨音这类共字同音词）**：这才是外扩的真实收益——【函数级】验证 "名天→明天" 今天同样被剪成单字 名→明 拒学，**而这恰是最常见的中文识别错误形态**（同音词差一字）。
3. 结论：**值得做，但只做保守版**——仅当去前后缀后任一侧剩单个 CJK 字时，把边界回扩 1 字（复用被剪掉的共同前/后缀），改后的词仍须满足 2-6 字纯中文门槛。风险受双保险控制：学词侧门槛不变 + 应用侧同音才替换，"后天"这类语义改写词学进去也是惰性噪声。~8 行。
4. 【未验证】本机无中文口播条件，中文学词全链路（含外扩后）仍需真机验证，建议修复方 PR 里配函数级用例。
