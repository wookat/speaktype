## ① About 升级横幅限流问题设计论证（不改代码）

现状【源码 index.ts:318-336 + 实测】：启动 5s 后匿名拉一次 `releases/latest`，失败静默、内存记忆化、无持久缓存、无重试；hosts 封 api.github.com 实测——About 页无横幅、无错误、无卡顿（静默降级本身正确）。

问题定量：匿名 GitHub API 限额 60 次/时/IP。个人独享 IP 下自用完全够；**共享出口 IP（公司 NAT/校园网/VPN）下同 IP 其他流量可轻易耗尽限额**，这类用户升级提示可能长期不出现——错过安全修复类版本才是真代价。

建议修法（~15 行，低风险，建议 v0.15.x 顺手做）：
1. **持久缓存**：成功拉到 tag 后连同时间戳写入 speaktype.json（`latestTagCache: {tag, at}`）；启动时缓存 <24h 直接用，不发请求——顺带把整体 API 消耗降到 ≤1 次/天/用户，反而更不容易撞限流。
2. **失败延时重试**：首拉失败后 setTimeout 30min 再试一次（上限 2-3 次）；配合缓存，一次成功可管一天。
3. 不建议做：带 token 请求（暴露面）、改用 releases 页面刮 HTML（脆弱）、频繁轮询（多余——非自动更新，提示晚几小时无害）。

## ② 增强标点 × 词典热词组合深挖（长期未审组合面）【实测】

组合链路【源码 polish.ts:326-329】：cleanup → 增强标点模型 → ITN → 词典热词纠错（热词在标点之后）。

### P3-①：原文已有逗号处标点模型再补句号 → 落字出现「great,. So」连续标点

- 复现【实测】：parakeet + 增强标点开启，口述含逗号的长句 → raw=`…it worked great, so we should…`，落字=`…it worked great,. So we should…`——逗号+句号连排（实拍+history 核对）。
- 根因【源码】：punct 模型在已有「,」后再断句补「.」；toEnglishPunct 的去重只收敛 `[.?!]` 连排（polish.ts:208 `/([.?!])[.?!]+/`），不处理「,.」混排。
- 修法 ~1 行：去重正则扩为逗号与终止标点混排时保留终止标点，如补 `out.replace(/,([.?!])/g, "$1")`。CJK 分支「，。」混排同理【推测，未实测】，建议一并核。
- 严重度：P3——触发需「原句已带部分标点 + 仍过 needsPunctuation 门槛」的中间地带，但一旦触发落字即带明显语病，用户需手改。
