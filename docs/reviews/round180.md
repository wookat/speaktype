## 一、问题清单

### P1-1 快速退出免按模式时，进行中片段静默丢字（新发现，确定性复现 2/2）

- **复现步骤**：
  1. Alt+Q 进入免按模式，开始说话；
  2. 说话开始约 2.5s 内再按 Alt+Q 退出，且 Alt 键在退出后继续按住约 160ms（真实用户按组合键的正常节奏，先松 Q 后松 Alt）；
  3. 观察目标窗口（记事本）。
- **现象**：识别结果正常进历史（无 failed 标记）、悬浮条显示「润色中」，但目标窗口**没有落字，也没有任何失败提示**——文字静默消失。
- **根因（判别实验证实，非猜测）**：落字走 `paste.ts` 的 SendInput Ctrl+V。短片段本地识别极快，Ctrl+V 在物理 Alt 尚未松开时发出，实际变成 Ctrl+Alt+V，被目标程序忽略。对照实验：同样 2.5s 快速退出，Alt 立即释放 → 落字成功（+14 字）；Alt 多按住 160ms → 丢字（2/2 复现）。较长片段（≥3.4s）因识别耗时错开了 Alt 按住窗口而正常落字，所以此 bug 专坑「短句+快退出」。
- **建议修复**：`pasteText` 前用 GetAsyncKeyState 检测并等待修饰键（Alt/Ctrl/Shift/Win）物理释放后再发 Ctrl+V；或延迟粘贴至无修饰键按下（可设 ~1s 上限，超时仍粘贴并记日志）。

## 三、竞品对照：我们仍缺的高价值能力 Top3

对照 Wispr Flow（2026-08 文档/官网）、Handy v0.9.5（2026-08-08）、CapsWriter-Offline v2.6：

1. **上下文感知（前台应用 + 屏幕文本自适应）** —— Wispr Flow 的 Context Awareness（默认开启）会读取活动应用与光标附近少量文本：按应用类别（邮件/工作 IM/个人 IM/其他）自动匹配语气风格，并用屏幕上可见的人名/收件人来纠正专有名词拼写，浏览器内还能识别到具体网站（Gmail/Notion 单独识别）。我们只有「按应用手动配规则切人设」，不读屏幕上下文，人名同音错字仍靠事后学词。这是「识别准确率+落字风格」两个维度的代差，且与我们已有的人设/词典架构天然衔接（可做成可选项守住隐私边界）。
2. **流式/低延迟识别与 GPU 加速** —— Handy v0.9.0 起集成 transcribe.cpp 支持真流式模型；CapsWriter v2.5/2.6 引入 Qwen3-ASR-1.7B GGUF（Vulkan/DML GPU 加速，实测转录延迟 100-300ms，另有 GPU 预加速锁频配置）。我们的离线 partial 是每 ~1s 对整段缓冲重解码、主进程同步解码长句时会短暂卡 UI，落字延迟与字幕流畅度对比明显吃亏。引入流式 ASR（或 sherpa-onnx streaming 模型）+ 解码移出主进程是字幕体验的下一个台阶。
3. **语音 Snippets + 边说边改（backtrack）** —— Wispr Flow 支持语音触发的 Snippets（说 cue 词即插入整段格式化文本，如日程链接/自我介绍/FAQ），并能实时理解口语纠正（「不对，改成…」backtrack）、自动编号列表。我们只有本地口语清理（「5 点，不对，6 点」→「6 点」的简单规则）和 F8 选中改写，没有用户可自定义的语音短语库。Snippets 实现成本低（词典架构可复用），对高频输入者是每天省几十次复制粘贴的硬价值。

（次级观察：CapsWriter 的「日记功能」「带延迟附加回车」「动态热词」、Handy 的「粘贴时保留非文本剪贴板内容」也值得排期；其中剪贴板保留与我们 Ctrl+V 落字路径直接相关。）

## 四、「是否有更好设计」反问与建议

1. **免按退出的语义**：快速 Alt+Q 退出时，进行中的短片段该落字还是该丢弃？目前实现是「落字但可能因竞态丢失」（P1-1）。更好的设计或许是明确二选一：要么保证落字（等修饰键释放再粘贴），要么把「退出即丢弃进行中片段」做成明确行为+toast 告知——最差的是现在这种「有时落有时丢、不告诉用户」。
2. **落字失败兜底**：所有粘贴路径（不只免按）都值得加「粘贴未生效 → 提示已在剪贴板」的兜底（见 P3-1），把「静默失败」从产品里彻底消灭。
3. **来源筛选的扩展性**：#268 的筛选目前是「听写/文件」二元。等手机麦克风、改写（F8）等来源的历史条目多起来后，是否直接升级为多来源 chips（可多选）？现在的下拉单选架构升级成本低，建议在下一个历史页迭代时一并考虑。
4. **长句字幕**：20s 滑窗滚动本轮观感合格，但 30s+ 长句「字幕内容 < 最终落字内容」的差异用户无从知晓。是否在悬浮条加一个轻量「仍在聆听/已缓冲 Ns」指示，管理超长句时的用户预期？
